# Подготовка Сферорумии к запуску в играх ВКонтакте

Актуализация 10.11.2026: выбран бесплатный MongoDB Atlas HeroEther, подключено гибридное сохранение с локальным WAL. PostgreSQL и рекомендации аренды ниже являются прежним вариантом, их не применять как текущую конфигурацию. Актуальны [хранилище MongoDB](../../docs/mongodb-storage.md) и [разбор архитектуры / тестовая подготовка входа](../../docs/architecture-advice-20261110.md). VK-вход и реальные платежи выключены; стенд `auth/` работает только с отдельными тестовыми БД. Прежний VPS не используется.

Обновление от 25 октября 2026: выбор комнат и распределение мест подключены к локальному серверу. Рабочая политика перенесена в `config/arena-rooms.json`, общая модель — в `src/server/arena/arena-directory.js`. Файл модели в этой папке переэкспортирует её для сохранения проверок. Комнаты пока работают в одном процессе с общим JSON-хранилищем. Актуальные API и ограничения: [правила арен](../../docs/rules/arenas.md). Описанные ниже PostgreSQL, распределённые workers, VK-вход и инфраструктура по-прежнему являются заготовками; прежние оценки производительности не подтверждают текущую ёмкость.

Памятка владельцу и разработчику. Расчёт на **400 одновременно играющих участников и ещё 30 пользователей в лобби**, по состоянию на **20 октября 2026 года**. Целевая платформа — раздел «Игры» внутри ВКонтакте, покупки за голоса.

Рекомендуемая основа: собственные серверы Node.js для арен, PostgreSQL для профилей и экономики, HTTPS/WSS для соединения с браузером, отдельное хранилище резервных копий. VK предоставляет платформу запуска и платежей; игровую симуляцию и сохранения размещаем на своей инфраструктуре.

**Арендовать мощный сервер и скопировать туда текущую игру пока недостаточно.** В коде нужно разделить арены, заменить файловое хранилище, подключить проверенную авторизацию VK и сократить сетевые сообщения. Подготовленные файлы перечислены ниже. Они не подключены к `server.js`, не меняют локальную игру и не запускают платные ресурсы.

## Правила открытия арен

Арена — отдельная игровая комната, а не отдельный арендованный компьютер. Несколько арен могут работать на одной машине в отдельных процессах или в ограниченных группах.

| Участников на аренах с учётом кратких броней | Открытых арен | Вместимость комнат |
| ---: | ---: | ---: |
| 0–79 | 3 | 105 |
| 80–149 | 5 | 175 |
| 150–219 | 7 | 245 |
| 220–289 | 9 | 315 |
| 290–359 | 11 | 385 |
| 360–400 | 13 | 455 |

Правило продолжения: когда до суммарной вместимости остаётся 25 мест, подготовить ещё две арены. Поэтому после 80 следующий порог 150, далее 220, 290 и 360. Брони включены в расчёт, чтобы одновременные нажатия «Играть» не переполняли комнату. Принятый предел нагрузки — 400 участников арены, даже когда суммарно комнаты имеют 455 мест.

Три начальные арены должны быть готовы до открытия публичного входа. Остальные уже размещаются на оплаченных машинах: открытие комнаты не должно ожидать заказа новой виртуальной машины. В идеале worker-процессы прогреты заранее.

Список около «Играть» показывает `Арена 1 · 28/35`, статус и доступность. При открытии новых комнат они появляются в списке; состояния «Подготовка» и «Недоступна» не принимают игроков. По умолчанию вход наполняет уже используемые комнаты. Выбор пользователем конкретной арены сохраняется, пока там есть место.

Если выбранная арена заполнена или недоступна, сервер атомарно бронирует место на другой и сообщает об изменении выбора. Если мест нет, сервер возвращает `ARENAS_FULL`, а интерфейс показывает ровно:

> Сейчас все арены заняты, попробуйте позже

Бронь действует 15 секунд и используется один раз. Незавершённое подключение освобождает место. Одна учётная запись не может одновременно занять две арены. При выходе в лобби место освобождается только после завершения прежней игровой сессии.

**Лобби учитывается отдельно.** Максимум одновременно присутствующих профилей — 430, из них максимум 400 играют или подключаются к арене. При 400 играющих остаётся 30 мест для лобби. Когда играющих меньше, в лобби может быть больше 30 человек. Повторная вкладка того же профиля не считается новым человеком; технический предел сокетов задаётся отдельно.

В заготовке дополнительные арены сохраняются до перезапуска. Автоматическое закрытие комнат не реализовано. Если оно понадобится, закрывать только пустые комнаты после 10 минут простоя, по две, оставляя минимум три; игроков не переселять посреди жизни.

## Что показал текущий код

| Сейчас | Что требуется перед публичным запуском |
| --- | --- |
| Одна `Arena` на экземпляр `createGameServer`, максимум 32 WebSocket | Реестр комнат и жёсткий предел 35 на каждую |
| Сервер считает движение, массу, поглощение и бустеры | Сохранить серверный расчёт; клиент посылает команды, а не итоговый урон/баланс |
| Тик 50 мс, до 16 частей игрока, 200 частиц эфира, до 1024 выброшенных частиц | Проверять тяжёлые бои и загрузку CPU на 13 комнатах |
| Полный JSON состояния всем участникам 20 раз в секунду | Снимок при входе, затем изменения, область видимости и компактные координаты |
| `profiles.json` переписывается синхронно через временный файл | Асинхронные транзакции PostgreSQL и отдельные строки профилей |
| Сессия определяется cookie; возможен вход WebSocket без профиля | Серверная проверка VK, обязательная сессия и одноразовый билет арены |
| Тестовые покупки начисляют продукт по подтверждению игрока | Публичная выдача только после проверенного уведомления VK |
| Ограничение запросов по адресу TCP-соединения | Учёт доверенного reverse proxy и лимиты по профилю, дополнительно по IP |

Замер на этом ПК — Ryzen 5 2600, Node.js 24.22.0, 35 участников, 120 измеряемых тиков после прогрева. Участники неподвижны и защищены от поглощения, чтобы количество тел не уменьшалось. Файлы профилей, TLS, сокеты, настоящая БД и активные бустеры в замер не входят.

| Сцена | Средний снимок | Тик и сериализация p95 | Расчёт исходящего канала при 400 игроках |
| --- | ---: | ---: | ---: |
| 1 часть на игрока | 59 171 байт | 1,62 мс | 3,79 Гбит/с |
| 16 частей на игрока | 127 248 байт | 8,52 мс | 8,14 Гбит/с |
| 16 частей и 1024 выброшенных частицы | 234 682 байта | 12,76 мс | 15,02 Гбит/с |

Формула канала: `средний размер снимка × 20 обновлений × 400 получателей × 8`. Это экстраполяция одинаково заполненных комнат, а не проведённый сетевой тест 400 клиентов. Реальные имена, эффекты, дополнительные события и TLS меняют результат.

**Обязательный этап — оптимизация протокола.** Целевой бюджет для проверки: в среднем 10–30 КБ/с на игрока и не более 100–150 КБ/с в тяжёлых сценах. Эти значения пока не достигнуты и не измерены. При 400 игроках средний целевой канал составит 32–96 Мбит/с; для пиков и загрузки ресурсов нужен порт 1 Гбит/с с подтверждённой полезной полосой. Интерполяция между снимками помогает сохранять плавность при более редкой рассылке. [Материал автора сетевых игровых технологий о snapshot interpolation](https://gafferongames.com/post/snapshot_interpolation/).

Даже оптимизированные 32–96 Мбит/с при непрерывной полной нагрузке дают примерно **10,4–31,1 ТБ за 30 суток**. У реального проекта средняя посещаемость обычно ниже пика, но трафик нужно считать отдельно от CPU. В Selectel для облачных серверов страница указывает 3 ТБ включённого трафика; Timeweb заявляет безлимитный трафик для VPS. Условия конкретной конфигурации и допустимую постоянную полосу необходимо подтвердить при заказе. [Selectel](https://selectel.ru/services/cloud/servers/), [Timeweb](https://timeweb.cloud/services/vds-vps).

## Какую инфраструктуру выбирать

Для начала предлагаю запросить **Timeweb Cloud Dedicated High CPU в Москве** и сопоставимый расчёт **Selectel HighFreq**. Высокая производительность одного ядра важна для серверного тика; обычный shared-хостинг сайтов для нашей архитектуры не подходит. У Timeweb линейка Dedicated High CPU описана как выделенные процессорные ядра, NVMe и частота 5 ГГц; конкретную конфигурацию необходимо проверить в панели. [Описание линеек Timeweb](https://timeweb.cloud/docs/cloud-servers/manage-servers/create-server).

Это стартовая конфигурация для нагрузочного стенда и последующего запуска **после оптимизации протокола**:

| Ресурс | Начальная конфигурация | Для чего |
| --- | --- | --- |
| 2 игровых узла | Каждый: 8 выделенных высокочастотных vCPU, 16–32 ГБ RAM, 120–160 ГБ NVMe, порт 1 Гбит/с | 6 и 7 арен; несколько Node.js процессов, а не один на все ядра |
| Узел API и координатора | 2–4 vCPU, 4–8 ГБ RAM, 60 ГБ SSD | Вход VK, лобби, реестр комнат, nginx, операции профиля |
| PostgreSQL | Начать с 4 vCPU, 8 ГБ RAM, 100 ГБ SSD на основной ноде; реплика с управляемым failover | Профили, экономика, кланы, журналы, платежи |
| Хранилище копий | Отдельный приватный S3 bucket, стартовый бюджет 100–300 ГБ | Зашифрованные выгрузки, отдельные права доступа |
| Наблюдение | Метрики, логи, внешний контроль доступности | Перегрузка тиков, ошибки сохранения, диски, копии |

Все игровые узлы и БД разместить рядом, с приватной сетью; из интернета открыть только HTTPS 443, HTTP 80 для перенаправления и административный доступ с ограниченных адресов. PostgreSQL и worker RPC не публиковать наружу. ОС — Ubuntu 24.04 LTS или согласованный поддерживаемый Linux. Для Node.js выбрать поддерживаемую LTS-ветку; на дату подготовки Node.js 24 имеет статус LTS, а 20 — EOL. [Официальный график Node.js](https://nodejs.org/en/about/previous-releases).

Два игровых узла уменьшают масштаб одной аварии, но **не обеспечивают автоматическое сохранение всех боёв и вместимость 400 человек при потере одного узла**. Для этого нужен подтверждённый тестом резерв N+1, например третий игровой узел, а также резервирование координатора и gateway. PostgreSQL с одной нодой также остаётся точкой отказа.

Плановый бюджет выбранной схемы — **около 35–65 тыс. ₽ в месяц** до специальных услуг защиты и возможного платного трафика. Это наш резерв бюджета, **не полученная оферта**: ориентир 20–36 тыс. за два игровых узла, 8–18 тыс. за БД с репликой, 2–5 тыс. за API и 1–3 тыс. за копии/наблюдение, плюс запас. Точную сумму согласовать по одной корзине с регионом, НДС, IP, сетями, резервированием и трафиком.

Для более простого размещения на одной физической машине есть конкретный ориентир Selectel **BL24-NVMe: Ryzen 9 9950X, 16 ядер, 128 ГБ ECC, 2 × 1920 ГБ NVMe — 49 100 ₽/мес. на странице каталога**. Это цена самого сервера; БД, независимые копии и услуги сети считаются отдельно. Памяти для нашего первого запуска здесь много с запасом, а отказ машины остановит все её арены. Перед оплатой проверить наличие и цену. [Каталог Selectel](https://selectel.ru/services/dedicated/amd-ryzen-epyc/).

Дешёвый тестовый стенд можно начать с одной ВМ 4–8 vCPU и 8–16 ГБ RAM. Он нужен для интеграции VK и измерений; заявлять поддержку 400 игроков на основании такого стенда нельзя. Покупать сразу 13 машин не требуется.

## Что подготовить владельцу

1. Кабинет разработчика и игру в разделе «Игры» VK; идентификатор приложения, доступ к настройкам и секретный ключ. Дать разработчику нужную роль, не передавать пароль от личного VK.
2. Собственный домен, например `game.<ваш-домен>`, и отдельный адрес тестовой версии `staging.<ваш-домен>`. Нужен доступ к DNS для записей и TLS-сертификатов.
3. Аккаунт хостинга с оплатой и отдельными доступами разработчика/администратора. Заказать сначала стенд, затем подтверждённую нагрузочными тестами конфигурацию.
4. PostgreSQL с выбранной версией 17 или 18, приватным адресом, сертификатом CA, отдельными ролями игры, миграций и копирования.
5. Отдельный bucket для копий и место хранения закрытого ключа расшифровки. Без этого ключа зашифрованные копии восстановить нельзя.
6. Тестировщиков VK, карточку игры, иконку, скриншоты, описание, контакт поддержки, пользовательские документы. Актуальный состав требований и условия монетизации сверить в кабинете перед отправкой.
7. Таблицу товаров: внутренний `productId`, название, цена в голосах и выдаваемый продукт. Действующий каталог игры — `public/shared/virtual-product-catalog.js`; цену и награду утверждает сервер.
8. Рабочий адрес для сигналов об авариях, ответственного за резервные копии и согласованные сроки восстановления.

Платформа выбрана именно VK Games. Примеры Mini Apps и VK Play нельзя автоматически использовать как спецификацию входа нашей игры. В официальном примере VK Direct Games покупки вызываются через `VKWebAppShowOrderBox`, а обработчик платежей задаётся в настройках приложения. [Официальный пример VKCOM](https://github.com/VKCOM/vk-direct-games-example).

Полные страницы `dev.vk.com` при подготовке не открылись. Поэтому точный вариант подписи авторизации, формат уведомлений и актуальные требования модерации оставлены обязательной проверкой по документации **созданного приложения**. В код не добавлена предположительная проверка от другого типа приложений. Официальный [VK Bridge](https://github.com/VKCOM/vk-bridge) понадобится для взаимодействия с оболочкой VK.

## Порядок запуска

1. Разработчик выполняет этапы из [технической памятки](developer-guide.md) на отдельной тестовой ветке/копии. Локальная версия остаётся рабочей.
2. Создаётся тестовое приложение VK и отдельная БД. Вставляются параметры из `.example`, подключается HTTPS, авторизация проверяется на двух разных VK-профилях.
3. Проверяются настоящие тестовые платежные уведомления VK и повторная доставка уведомления; клиентская кнопка не может сама начислять покупку.
4. Проводится сетевой тест 400 игровых и 30 лобби-сессий, тяжёлый бой, авария worker, перезапуск API и восстановление БД из копии.
5. Владелец получает итоговый отчёт по CPU, каналу, задержкам, сохранности покупок и месячной стоимости. По нему выбирается окончательный тариф.
6. Производственные домен, приложение, секреты и БД отделяются от тестовых; перенос данных выполняется по плану миграции. Открытие каталога VK — после успешных проверок.

Результат текущего этапа — исследование, расчёт, проверенная модель распределения и выключенные заготовки. Публичный сервер не развёрнут; аренда и платные услуги не оформлялись.
