# Сохранение данных и восстановление после аварии

Для игры нужно различать долговечные данные профиля и текущее состояние боя. PostgreSQL хранит профили, покупки, валюту, предметы, достижения, кланы и подтверждённый прогресс. Координаты шаров и эффекты текущего тика находятся в памяти worker. Резервная копия базы не восстанавливает автоматически все летящие снаряды.

## Защита базы данных

В PostgreSQL оставить `fsync=on`, `full_page_writes=on` и `synchronous_commit=on`; успешную выдачу подтверждать после COMMIT. WAL позволяет восстановить согласованность при сбое процесса/ОС. Для восстановления после потери всей машины требуются копия базы и архив WAL, либо подготовленная реплика. Обычный `pg_dump` не является заменой WAL/PITR. [Документация PostgreSQL](https://www.postgresql.org/docs/current/continuous-archiving.html).

Практичный вариант — Managed PostgreSQL с репликой и PITR. У Selectel документированы полный бэкап раз в неделю, дельта раз в день, WAL каждые 10 минут либо при накоплении объёма, хранение 7 дней. Восстановление создаёт новый кластер с новыми адресами. Не обещать нулевую потерю данных при аварии площадки на основании только такого архива. [Регламент Selectel](https://docs.selectel.ru/managed-databases/postgresql/backups/).

У Timeweb есть расписание физических копий PostgreSQL. Логические копии отдельно описаны как beta и создаваемые вручную; не считать эту опцию автоматически настроенным PITR. Перед заказом запросить фактический режим репликации, failover, архивирования WAL и целевой RPO. [Физические копии](https://timeweb.cloud/docs/dbaas/dbaas-manage/backup), [логические копии](https://timeweb.cloud/docs/dbaas/dbaas-manage/logical-backups).

Для самостоятельной PostgreSQL можно использовать pgBackRest с S3 и архивированием WAL, но это требует администратора. Начальная цель: полный бэкап еженедельно, дифференциальный ежедневно, непрерывное архивирование WAL с контролем задержки, срок 14–30 дней. Конфигурацию и восстановление проверить по выбранной версии. [Официальное руководство pgBackRest](https://pgbackrest.org/user-guide.html).

## Независимая копия каждые шесть часов

Подготовленный `backup-postgres.js` делает логический дамп `pg_dump -Fc`, проверяет его каталог через `pg_restore --list`, шифрует публичным ключом age и загружает в отдельный S3 bucket. Маркер `complete.json` с размером и SHA-256 появляется только после успешной загрузки зашифрованного файла. Проверка каталога не доказывает возможность полного восстановления — это проверяется отдельно.

Скрипт по умолчанию выключен. Он **не установлен** в планировщик и **не подключён** к какой-либо БД. Для включения на отдельном Linux-узле:

1. Установить Node.js LTS, PostgreSQL client нужной основной версии, `age`, AWS CLI.
2. Создать пользователя `sferorumiya-backup`, отдельную читающую роль PostgreSQL и приватный S3 bucket.
3. Заполнить `/etc/sferorumiya/pg_service.conf` и `/etc/sferorumiya/pgpass`; права 600, владельцем backup-пользователь. Параметры host, dbname, user выдаёт администратор БД. Проверять TLS сертификат через CA. [Формат service-файла PostgreSQL](https://www.postgresql.org/docs/18/libpq-pgservice.html).
4. Создать пару ключей age. На сервер скопировать только публичный recipient. Закрытый ключ положить в защищённое хранилище владельца и резервное место. [Установка и использование age](https://github.com/FiloSottile/age).
5. Скопировать `backup.env.example` в `/etc/sferorumiya/backup.env`, заменить все `REPLACE...`, выставить `BACKUP_ENABLED=true`. Настоящий файл в Git не добавлять.
6. Из `backup-systemd.example` создать два unit-файла, убрав ведущие `#` у строк каждого соответствующего блока. Проверить пользователя, пути и доступ к утилитам.
7. Выполнить один ручной запуск service, скачать результат и восстановить в **новую тестовую БД**. После проверки включить timer.
8. Настроить lifecycle для префикса `snapshots/`: хранить 30 дней. Для длительного архива отдельно сохранять одну месячную копию, например 12 месяцев; это дополнительная настройка, которой скрипт не делает.

Расписание шаблона: 00:15, 06:15, 12:15, 18:15 UTC, то есть 03:15, 09:15, 15:15, 21:15 Москвы, с задержкой до минуты. Обновление ежедневных игровых бонусов в 00:00 Москвы — отдельный механизм.

Backup-ключу S3 не выдавать право удаления копий или изменения политики хранения. Желательно отдельный проект/аккаунт и поддерживаемая провайдером защита от удаления. Если загрузка оборвалась, набор без `complete.json` не считается годной копией; lifecycle затем убирает остатки.

Сигналы: service завершился ошибкой; нет новой полной копии более 7 часов; недостаточно места; растёт очередь WAL; реплика отстаёт; истекает сертификат. Контроль выполнять извне: упавший сервер не способен сообщить о собственной полной недоступности.

## Проверка восстановления

Не восстанавливать поверх рабочей БД. Создать отдельную пустую `sferorumiya_restore_check` на том же основном выпуске PostgreSQL, подготовить роли/расширения отдельно: дамп приложения не содержит всех глобальных настроек кластера.

Скачать `database.dump.age` и соседний `complete.json`; сверить SHA-256 зашифрованного файла с манифестом. Затем на доверенном компьютере с закрытым ключом:

```bash
age --decrypt -i /secure/backup-key.txt -o database.dump database.dump.age
pg_restore --exit-on-error --no-owner --no-privileges \
  --dbname=sferorumiya_restore_check database.dump
```

Подключение задаётся через отдельные проверенные PG-параметры, не через production-профиль по умолчанию. Перед командой проверить имя целевой БД. Не добавлять `--clean` к рабочей базе.

Проверить количество игроков и кланов, контрольные профили, балансы, VIP/Premium, инвентарь, уникальные покупки, достижения и историю суточных бонусов. Запустить тестовую игру с этой БД. Повторить платежное уведомление: выдача не должна повториться. Измерить время всей процедуры, включая скачивание и проверку.

Проводить проверку восстановления минимум раз в месяц и после изменений схемы или backup-инструментов. Пароли, роли, CA, конфигурацию приложения и инструкции восстановления хранить отдельно от самой БД.

## Ожидаемое поведение при авариях

| Сбой | Поведение, которое нужно реализовать и проверить |
| --- | --- |
| Перезапуск API | Подтверждённые операции в PostgreSQL сохраняются; повтор requestId возвращает прежний ответ |
| Падение worker | Закрываются его арены; профили сохраняются; текущий бой может завершиться технически |
| Отказ PostgreSQL | Новые покупки, награды и траты не подтверждаются до восстановления; идемпотентные события повторяются |
| Потеря диска/узла БД | Failover на реплику либо восстановление нового кластера; возможная потеря зависит от режима репликации/WAL |
| Ошибочная массовая выдача | Остановить новые мутации, сохранить текущую копию, восстановить в отдельный кластер и сверить журнал; не откатывать платежи вслепую |
| Полная потеря основной площадки | Поднять инфраструктуру из конфигурации, восстановить копию/WAL и доступы, проверить экономику, переключить DNS |

Начальные **цели**, а не гарантии: восстановление API/worker за несколько минут, восстановление данных до часа после учебной проверки; для архивного восстановления Selectel закладывать до 10 минут последних изменений плюс фактическую задержку архива, для независимого дампа — до 6 часов. Если требуется почти нулевая потеря подтверждённых платежей при потере узла, отдельно выбирать синхронную репликацию и тестировать её поведение.

Полное продолжение боя после падения worker — отдельный этап: снимок состояния арены, состояния генератора случайных чисел и игрового времени, журнал команд/событий, последовательность восстановлений и защита от двойной выдачи. Для первого запуска практичнее сохранять экономику надёжно, а оборванную жизнь завершать по утверждённому правилу с однократной компенсацией при необходимости.
