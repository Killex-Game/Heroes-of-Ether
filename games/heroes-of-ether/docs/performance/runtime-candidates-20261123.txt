Календарь брака
social-calendar.settle занял 4.57% self CPU в этом live-срезе. При проверке
даже одного женатого профиля он строил новую Map всех 1706 профилей.
Теперь используется существующий profile-index с immutable-table-delta.
Кеш содержит только ID -> ключ, сам супруг всегда читается из текущего мира.
Новая личность, удаление или неизвестное происхождение таблицы перестраивают
индекс по прежним правилам. Награды и календарные границы не меняются.
Проверенная копия реального мира: 1706 профилей, 16 состоящих в браке.
Полные JSON-хеши прежнего и нового результата равны для текущих суток,
следующих суток, обратного времени, смены клана, развода и удаления супруга.
Пять чередующихся локальных измерений по 2000 неизменённых scoped-проверок:
прежний код 1086-1276 мс, кандидат 1.92-3.60 мс. Это только эта функция,
не обещание ускорения всей игры. Неизменность исходного мира проверена.

Передача еды рабочему потоку
Если список полностью состоит из прежних замороженных примитивных записей
в прежнем порядке, encode возвращает null без новых Map/массивов/буферов.
Геттеры, вложенные изменяемые значения, движение, перестановка и удаление
остаются на прежнем пути сравнения значений. Формат передачи не изменён.
Микротест 10000 кадров: 300 статичных записей 340.64 -> 4.97 мс,
1224 статичных 1346.50 -> 21.24 мс. Это частный сценарий, не whole-game A/B.
На движущихся данных выигрыша не установлено. Однократный packed moving
прогон был хуже: 1245.42 -> 1350.62 мс. Этот результат сохранён и не скрыт.
Не делать вывод о полезности включения только из статичного микротеста.
