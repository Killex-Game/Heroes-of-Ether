# MongoDB, вход VK и дальнейшее масштабирование

Проверено 10.11.2026. Работа только локальная и на уже подключённом бесплатном Atlas HeroEther. Новых сервисов, платных тарифов и npm-зависимостей нет. Действующие профили, физика, награды, вход и покупки не менялись; перезапуск игры не потребовался.

## Решения по полученным советам

| Совет | Решение для нашей игры |
| --- | --- |
| Клиент -> Node.js -> MongoDB | Верно. Браузер не получает доступ к БД. Сейчас игровой сервер использует память и долговечный локальный журнал, а MongoDB получает подтверждённые снимки в отдельном Worker. Это гибридный режим, не готовая полностью облачная экономика. |
| Проверять личность игрока | Подготовлен отдельный проверяющий модуль для формата VK Mini Apps. Он не подключён к HTTP или WebSocket. Для Games/ОК нужен подтверждённый формат конкретного приложения. |
| Создавать аккаунт при первом входе | Проверен отдельный MongoDB-стенд: привязка и профиль создаются одной транзакцией. Уникальность по площадке, приложению и пользователю. Повторы не выдают стартовый баланс снова. |
| Проверять покупки на сервере | Уже применяется. Клиент сообщает идентификатор продукта; цена, право покупки, состав и квитанция определяются сервером. Перенос экономических операций в MongoDB потребует асинхронного хранилища и сохранения всех нынешних проверок и квитанций. |
| Хранить позиции и комнаты в Redis | Для текущего одного процесса достаточно RAM Node.js. Redis не ускорит автоматически физику и добавит сетевые обращения. Вернуться к нему при реальном распределении координатора, присутствия и комнат между процессами. |
| Переписать сеть на Colyseus/Socket.io | Сейчас не требуется. Уже работают `ws`, комнаты, бронирование, подтверждения, дельты состояния и обработка медленных клиентов. Смена транспорта потребует повторной проверки всех механик и не доказана замерами как решение лагов. |
| Запустить `pm2 -i max` | Не применять к нынешнему `server.js`. Профили и комнаты находятся в памяти одного процесса, а MongoDB-зеркало допускает одного писателя. Независимые процессы не получат автоматически общий игровой мир. |
| HTTPS/WSS | Нужно для публичного размещения; шаблон nginx уже есть. Домен, сертификаты, iframe и вход через площадку проверяются на новом стенде отдельно. Прежний VPS не используется. |
| Реальные платежи VK | Пока сохраняется тестовый адаптер. Не подключать пример callback как готовую оплату: подпись, статусы, товар, приложение, пользователь, сумма, повтор и возврат должны соответствовать выбранному API площадки. |

MongoDB заменяет способ постоянного хранения, а не JavaScript или Node.js. Подключение БД само по себе не исправляет задержки игрового тика.

## Что неправильно или неполно в примерах

- В HMAC-примере склеены значения без URL-кодирования. Это ломает проверку значений с пробелами, `&`, `+` и другими символами. Нужна однозначная обработка исходной строки, а не произвольный объект с потерянными дубликатами. Проверяются также приложение, пользователь и возраст запуска; сравнение подписи использует `timingSafeEqual`.
- Подпись запуска Mini Apps нельзя использовать как универсальный обработчик VK Games, ОК и платежей. Официальный пример VKCOM архивирован в апреле 2024 года. Новый модуль проверен на его публичном примере и синтетических подписанных запросах, но не на реальном запуске нашей карточки приложения. [Источник формата](https://github.com/VKCOM/vk-apps-launch-params), [пример Node.js](https://github.com/VKCOM/vk-apps-launch-params/blob/master/examples/node.js).
- `axios.get('https://vk.com', ...)` не вызывает метод проверки членства. Для этой задачи предусмотрен `groups.isMember`; тип токена и версию нужно сверять с выбранным методом, а не использовать Service Token для любого действия. Сервисный ключ не заменяет подтверждённую оплату. [Официальная схема методов VK](https://github.com/VKCOM/vk-api-schema/blob/master/groups/methods.json).
- Простая последовательность «прочитал баланс -> вычел -> записал» опасна при одновременных запросах. Нужны условная атомарная запись либо транзакция, уникальный ключ квитанции и повтор с тем же ключом. Ответ об успехе выдаётся после долговечного подтверждения. [Транзакции MongoDB](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/), [уникальные индексы](https://www.mongodb.com/docs/manual/core/index-unique/).
- PM2 требует вынести общее состояние из независимых процессов. Для нашей игры ещё нужны маршрутизация по владельцу комнаты, запрет двух активных жизней, один планировщик наград и согласованная экономика. [Ограничение из документации PM2](https://pm2.keymetrics.io/docs/usage/cluster-mode/).

## Реализованная подготовка

`deployment/vk-production/auth/vk-mini-app-launch.js` принимает исходную query-строку, ограничивает размер и число параметров, отвергает дубликаты и некорректное кодирование. Проверяет HMAC-SHA256, app ID, положительный user ID и `vk_ts`. Возраст по умолчанию до пяти минут, допустимое опережение часов 30 секунд - это наша предварительная политика, не заявленное требование VK. Подпись не выдаёт права из неподписанных полей. Полная проверка возвращает неизменяемую внутреннюю идентичность; объект, составленный из клиентского JSON, её не заменяет. Подписанный запуск можно повторить в допустимом окне для входа в тот же профиль: это не одноразовый билет WebSocket.

`deployment/vk-production/auth/mongodb-signup-sandbox.js` специально отказывается работать с `hero_ether`, `sample_mflix` и любыми БД, кроме случайной тестовой `hero_ether_test_<20 hex>`. Создаёт уникальные индексы и записывает профиль с привязкой в одной транзакции. При конкурентной регистрации повторяет целую транзакцию. Фабрика профиля должна быть чистой, серверной и может вызываться повторно. В тесте используется минимальный контракт 100 монет / 10 кристаллов / пустой инвентарь. Это не второй рабочий формат сохранения и не замена полной фабрике игры.

Для включения реального входа позже понадобятся подтверждённый тип приложения, секрет, тестовый подписанный запуск, собственные отзываемые сессии, проверка iframe, авторизация HTTP/WSS и согласованный перенос существующих профилей. Не связывать аккаунты по нику и не менять текущие cookie/UUID автоматически. Новые модули нигде не импортируются действующим сервером.

Исходный алгоритм реализован средствами Node.js без новой библиотеки. Публичный вектор проверки взят из VKCOM/vk-apps-launch-params, MIT, Copyright (c) 2018 VK.com; уведомление сохранено в `deployment/vk-production/auth/VKCOM-LICENSE.txt`. Это не аудит лицензий прежних ресурсов проекта.

## Диагностика текущей БД

```powershell
node scripts/deployment/mongodb-health.cjs
node scripts/deployment/mongodb-health.cjs --atlas
```

Первая команда читает только безопасный файл состояния. Вторая дополнительно проверяет соединение, ревизию облачного снимка и размеры доступных пользователю БД. Профили, переписка, URI и пароль не печатаются. `ok` означает успешную синхронизацию не старше 90 секунд; `stale`, `error`, `stopped`, `missing` различаются. Код завершения 2 означает проблему синхронизации или предупреждение объёма; 1 - ошибку самой диагностики. Это команда проверки по запросу, не установленная служба мониторинга.

На момент проверки: ревизия локальной синхронизации и Atlas 150505, последняя отправка около 13 секунд назад, ping 78,3 мс. Данные и индексы двух видимых БД занимали 153 587 353 байта (около 146,5 МиБ), включая учебную базу. Это разовый замер, не средняя задержка или нагрузочный тест. Учебная база сохранена. У ограниченного пользователя отчёт может видеть только часть БД; окончательный общий расход проверяется в Atlas.

Atlas Free ограничивает объём данных и индексов 0,5 ГБ, количество подключений 500, операции 100/с, трафик 10 ГБ в каждую сторону за скользящие семь дней. Число игроков не равно числу соединений с БД: текущий Worker использует пул до трёх прикладных соединений, плюс служебные подключения драйвера. [Официальные лимиты](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/).

Нельзя обещать достаточность Free для 350 игроков без измерения записей, трафика, размеров и задержки подтверждения. Уже введённое объединение изменений и отдельный Worker сохраняются. Разрыв Atlas не блокирует физику, но облачная копия отстаёт; сохранность тогда опирается на локальный WAL. Потеря диска до отправки в Atlas остаётся отдельным риском.

## Проверки и следующий этап

Локальные проверки: восемь прошли, включая защиту тестового репозитория от рабочей БД. Реальная проверка Atlas также прошла: пять конкурентных входов создали один аккаунт, повтор сохранил изменённые 93 монеты вместо новой стартовой выдачи, сбой после записи профиля полностью откатился, одинаковые ID в разных приложениях получили разные профили. Временная БД удалена тестом. Это девять различных успешных проверок, не девять нагрузочных сценариев игры. Полный набор игры в этом этапе не запускался; известные прежние 39 ошибок не считаются исправленными.

Следующий полезный этап MongoDB: испытать экономические операции и задержку фоновой записи при смешанной нагрузке лобби и арен на изолированных данных. Затем выделять асинхронное хранилище профилей и квитанций для полностью облачного режима. Не записывать одновременно напрямую из нового репозитория и старого зеркала в рабочую базу. Для распределённых комнат сначала нужен единый владелец каждой жизни и экономики; дополнительные процессы и Redis обсуждать по результатам этих измерений.
