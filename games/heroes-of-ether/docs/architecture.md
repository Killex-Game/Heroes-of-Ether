# Архитектура и соглашения

Проект и экосистема — **Killex**; название игры — **«Герои Эфира»**.
Клиентские модули используют пространство имён `Killex`, события интерфейса — префикс `killex:`. Стабильные имена cookie, настроек браузера и версий сетевого протокола собраны в `public/shared/platform-contract.js`: их значения сохранены для уже существующих игроков. Названия баз Atlas также остаются прежними; переименование папок не создаёт новую базу и не переносит данные между локальной игрой и VPS.

Рабочая игра находится в `Killex/games/heroes-of-ether`. В корне экосистемы находятся только игры, инструменты обслуживания, документация, материалы проверок и резервные копии. Временные копии старых выпусков не служат источником для дальнейшей разработки.

Ожидание ответа и запрет действия различаются через `public/shared/control-state.js`: `state(control, disabled, unavailable)` сохраняет защиту от повторного нажатия, а `data-pending` исключает оформление недоступной кнопки. В третьем аргументе учитываются только игровые ограничения — баланс, уровень, наличие предмета и допустимый режим. При изменении цены или доступности состояние пересчитывается из актуального профиля.

## Как проходит действие игрока

1. `public/index.html` подключает CSS и клиентские модули в установленном порядке.
2. `public/game-client.js` управляет переходами лобби → арена → результаты, вводом, WebSocket и кадрами рисования.
3. Модуль из `public/ui/` открывает нужное окно или отправляет команду серверу.
4. `src/server/game-server.js` проверяет сессию, формат и частоту запроса.
5. Профильные действия проходят через `ProfileStore`, клановые — через `ClanService`, действия на арене — через `Arena`.
6. Сервер возвращает подтверждение и актуальное состояние. Браузер обновляет видимые значения и анимацию.

Браузер не определяет итоговый урон, выдачу валюты, содержимое сундуков или результаты битв.

## Основные объекты

| Объект           | Ответственность                                               |
| ---------------- | ------------------------------------------------------------- |
| `ProfileStore`   | Профили, транзакции, миграции и атомарная запись файла        |
| `ClanService`    | Состав клана, права ролей, заявки и казна                     |
| `Arena`          | Живущие игроки, части шаров, масса, еда и серверный тик       |
| `Combat`         | Траектории бустеров, попадания, ловушки и контакт меча        |
| `BoosterEffects` | Поджог, периодический урон, разделение и восстановление массы |
| `TestBots`       | Временные участники тестовой арены и тестовые кланы           |

Профиль — сохранённые данные аккаунта. Игрок на арене — состояние текущей жизни.

С 25 октября `ArenaRooms` создаёт несколько отдельных `Arena` внутри одного процесса. `GET /api/arenas` и короткие одноразовые брони направляют игрока в конкретную комнату. WebSocket-снимки, физика и чат арены не пересекаются; профильные награды всех комнат проходят единую очередь сохранения. При отказе записи следующий шаг всех комнат ждёт повторного сохранения того же пакета. Политика и ограничения описаны в [правилах арен](rules/arenas.md).
`parts` содержит части разделённого игрока, `mainPartId` определяет ведущий шар.
`effects` хранит сроки эффектов, `swordBurns` — поджог отдельных частей.
Сроки арены измеряются по игровым монотонным часам; календарные сроки аккаунтов и кланов используют календарное время.

## Передача и отрисовка арены

### Сохранения во время игры, 13.11.2026

Рабочий сервер включает `ProfileStore({ journal: true })`. До ответа игроку изменённые профили,
кланы и связанные квитанции записываются одной записью в `profiles.json.wal` с номером ревизии
и SHA-256. Бустеры и пакеты прогресса используют асинхронную подготовку долговечного сегмента;
подтверждение и публикация следуют только после `fsync` и проверки актуальности исходного состояния.
Для синхронных операций лобби сохраняется обычный журналируемый путь. Неизменённые профили
в журнал повторно не включаются. Ошибка или устаревший черновик не дают успешного подтверждения.
Изменения готовятся отдельно от сохранённого состояния; опубликованные объекты нельзя менять на месте.

Раз в секунду журнал запечатывается в `profiles.json.wal-N`. Отдельный Worker восстанавливает
снимок, сериализует весь архив, записывает и синхронизирует временный файл, затем атомарно
заменяет `profiles.json`. Только после этого удаляет включённые сегменты. Арена в это время
продолжает писать новый журнал. Это один процесс игры с фоновым потоком сохранения, не кластер.

При запуске загружается снимок и все последующие записи журнала. Незавершённый последний
хвост активного файла игнорируется; повреждённая полная запись или пропуск ревизии останавливают
загрузку, не заменяют данные пустым профилем. Ошибка записи откатывает неподтверждённый append;
при невозможности отката новые записи запрещены. Ошибка checkpoint сохраняет журнал для
повторной попытки. При накоплении 64 МиБ несвёрнутых записей новые транзакции отклоняются.
Штатное завершение ждёт окончательного checkpoint.

Для резервирования работающей игры нельзя копировать только `profiles.json`: свежий прогресс
может находиться в WAL. VPS-скрипт резервирования воспроизводит согласованный префикс журнала
в отдельном процессе и архивирует самодостаточный JSON. При ручном восстановлении сырых файлов
нужно переносить снимок вместе со всеми `profiles.json.wal*` из одной остановленной копии.
Перед откатом к коду без поддержки WAL сначала остановить игру и выполнить checkpoint текущим
модулем. Старые утилиты не должны редактировать сохранения параллельно работающему серверу.

Проверки: `profile-journal.test.js`, `journal-profile-store.test.js`, сетевые сценарии
`state-stream-server.test.js` с настоящим журналом. Нагрузочное сравнение —
`scripts/benchmarks/room-input-load.cjs`, 35 синтетических игроков; `LOAD_JOURNAL=0` включает
старый способ записи для сравнения. Сам тест никогда не использует живые сохранения.

`src/server/arena/state-stream.js` обслуживает поток состояния отдельно для каждого соединения.
Для клиентов с `stateAck` сервер допускает до четырёх неподтверждённых снимков с
`stateSequence`, чтобы частота обновлений не ограничивалась одним сетевым оборотом.
При заполнении этой очереди или буфера сокета новые позиции заменяют ожидающий снимок.
Подтверждённые операции, чат и сохранённые
итоги жизни идут независимо и не отбрасываются. Старые клиенты получают полные снимки
с ограничением отправки при заполнении сокета. Валидный ACK не расходует лимит игровых
команд; повторные и поддельные ACK расходуют его.

Первый снимок содержит всю еду в `ether`, следующие — `etherDelta.upsert` и
`etherDelta.removed` относительно последнего отправленного снимка. Переподключение
начинается с полной карты. Только координаты еды в сетевом пакете округляются до 0,1;
масса и серверная физика сохраняют точность. Краткие визуальные события ожидают отправки
до двух секунд, не более 128 каждого вида. Награды и итоги жизни к ним не относятся.

`FoodRenderer` кэширует еду участками по 128 мировых единиц и перерисовывает только
изменившиеся участки. При движении камеры используются готовые слои; кэш ограничен
64 МиБ пикселей и очищается при выходе с арены. Ники используют ограниченный кэш
измерений текста, сбрасываемый при загрузке шрифтов.

Регрессии проверяют `state-stream.test.js`, `state-stream-server.test.js`,
`tests/browser/arena-state-performance.test.js` и `tests/browser/connection-lost.test.js`.
Нагрузочный браузерный тест использует синтетические профили, два браузера, до 15 ботов
и 1224 частицы. По умолчанию Chrome замедлен вчетверо; `CHROME_CPU_RATE=1` отключает
замедление. Это локальная проверка, не подтверждение готовности к 400 игрокам.

## Структура интерфейса

`public/ui/` разделён по предметным областям: `clans`, `boosters`, `profile`, `progression`, `cosmetics`, `accounts`, `rankings`, `shop`, `lobby`, `layout`.

Общие расчёты и каталоги находятся в `public/shared/`. Некоторые модули там также содержат Canvas renderer, который вызывается только браузером; их математические функции проверяются Node.js тестами.

Модальные окна открываются через `public/ui/layout/modal-stack.js`. Этот модуль задаёт порядок поверх остальных окон и восстанавливает фокус.

## Порядок CSS

Все подключения перечислены в `public/index.html`. Порядок сохранён при переносе, поскольку более поздние правила уточняют более ранние.

- `styles/base/`: шрифт, страница, арена и HUD.
- `styles/components/`: оформление конкретных окон и элементов.
- `styles/theme/`: кнопки, палитра, декоративные детали и аккаунты.
- `styles/layout/`: сетки, размеры, прокрутка и адаптация к экрану.

Новая правка должна попадать в существующий файл своего компонента. Имена вроде `update`, `new`, `fix2` для новых исходников не используются. Финальные настройки геометрии находятся в `layout/dialog-and-menu-sizing.css`, общие цвета аккаунтов — в `theme/account-colors.css`.

## Имена и формат

Файлы и папки используют английский `kebab-case`, например `clan-chest-rewards.js`.
Названия описывают предмет и роль: `-dialog`, `-renderer`, `-rules`, `-catalog`, `-store`.
Комментарий в начале модуля объясняет назначение по-русски.
Prettier задаёт единые отступы, переносы строк и оформление блоков.

Идентификаторы предметов, скинов, профилей, CSS-классы и имена сообщений являются контрактом сохранений или интерфейса.
Локальные переменные и функции используют `camelCase`, классы — `PascalCase`, неизменяемые правила и лимиты — `UPPER_SNAKE_CASE`. Суффикс `Ms` означает миллисекунды, `Seconds` — секунды, `Bytes` — байты; размеры памяти Worker подписаны `MB` в соответствии с API Node.js. Игровые правила остаются рядом со своей предметной областью, а не в одном глобальном файле констант. Временные буферы физики хранятся отдельно от сохраняемого состояния.

Переименование файла не требует менять этот контракт. Например, `vip-1` в сохранении указывает на `vip-king.png` через каталог.

## Проверки

`npm test` запускает `tests/unit` и `tests/integration`.
`npm run check:structure` проверяет синтаксис, импорты, подключения HTML/CSS, каталоги скинов и бустеров, а также назначения из списка переименований.
Браузерные сценарии запускаются отдельно из `tests/browser`.
Новые результаты проверок хранятся в `tests/artifacts`. Исторические результаты до очистки 26.10.2026 сохранены вне игры в `../../backups/obsolete-files-20261026/removed-files.zip`, вместе с проверенным манифестом SHA-256.

`npm run docs:refresh` обновляет справочники из исходников. После изменения правил полезно выполнять его вместе с тестами.

## Сохранения и запуск

Корневая точка запуска `server.js` остаётся короткой. Полный сервер находится в `src/server/game-server.js`.
Настройки запуска читает и проверяет `src/server/runtime/server-settings.js` до захвата файла сохранений и подключения к Atlas. Пределы ресурсов потоков подготовки снимков находятся в `arena/state-worker-policy.js`. Параметры комнат в `config/arena-rooms.json` задаются в игроках, комнатах и миллисекундах; `config/arena-state-workers.json` задаёт количество потоков и обслуживаемых ими комнат. Физика пока принадлежит основному процессу; дополнительные потоки подготовки снимков не превращают её в независимые комнаты.

После изменения стартовых JSON нужен штатный перезапуск. Боты читают свой отдельный конфиг динамически; события управляются через панель владельца. `npm run config:check` и `npm run doctor` позволяют проверить настройки и состояние без изменения данных. Ошибочные значения и неизвестные ключи стартовых настроек останавливают запуск с названием поля.

Рабочие профили: `data/profiles.json`. Блокировка второго процесса: `data/server.lock`.
Настройка ботов: `config/test-bots.json`.
Имена файлов внутри сохранения и схема профилей при перестройке не менялись.

## Производительность и граница готовности

Смешанный прогон с `LOAD_MINUTES` оценивается по каждому запрошенному минутному окну. Проверка требует полный состав окон, не менее 60 секунд в каждом и прежние пороги задержек, частоты, покрытия бустеров и сохранения. Медленную минуту нельзя скрыть средним за весь прогон. Обычный короткий сценарий по-прежнему требует все пять фаз. Пересчёт старого отчёта хранится отдельно от исходных результатов.

У стенда процессов комнат `shards[].measuredRooms` снимается до опустошения очереди при остановке; частоту физики считать по этим счётчикам и `shards[].elapsed`. Финальные `rooms` могут включать дополнительные шаги для завершения уже принятых команд и нужны для аудита. `barrierMs` отдельно измеряет время ожидания подтверждения бустеров и заполненной очереди прогресса, без двойного учёта пересекающихся интервалов. Частота физики, частота доставленных снимков и задержки успешных команд — разные показатели.

Минимальная целевая нагрузка — 700 одновременно играющих, то есть 20 комнат по 35 человек. Это цель, а не подтверждённая вместимость текущего релиза. Возможность открыть 700 сокетов без полноценного движения, деления, бустеров, событий и сохранения не считается её достижением. В отчётах отдельно указываются подключения, живые игроки, число частей, предложенные команды, успешные подтверждения и незавершённая очередь.

Панель владельца получает `/api/admin/performance` только по авторизованному запросу: частота и длительность серверных шагов, очередь прогресса/действий, число комнат/частей и память. Автоматического опроса нет. Замер `monitorEventLoopDelay` включает разрешение 20 мс; это не аппаратный FPS клиента. Кольцевые выборки ограничены по объёму и времени.

`npm run benchmark:capacity -- 3 local` запускает изолированную синтетическую нагрузку с локальным WAL. `LOAD_MINUTES=60` задаёт час смешанной нагрузки минутными окнами; `LOAD_MIXED_SOCIAL=1`, `LOAD_EVENT=black-friday` и `LOAD_STOCK=1000` включают подарки/прочтение, активное событие и запас бустеров. Для сравнения с текущим транспортом нужны одинаковые `LOAD_PACKED_PARTS=0`, `LOAD_PACKED_FOOD=0`, число state Worker и лимит обслуживаемых ими комнат на обеих сторонах. `LOAD_ACK_DIR` включает журнал наблюдавшихся успешных ответов, после штатного завершения `npm run benchmark:audit -- <каталог>` сверяет их с восстановленным WAL. `close-status.json` фиксирует остаток очереди после остановки. Режим `mongo` выбирается явно и создаёт отдельную тестовую базу с проверкой принадлежности; рабочие базы не используются как нагрузочные.

Прототип `scripts/benchmarks/resident-room-processes` изолирует физику и сетевые снимки в дочерних процессах, сохраняя одного писателя профилей. Это испытательный стенд без рабочего межсерверного допуска и передачи владения. `ROOM_BENCH_INPUTS=socket` передаёт движение, кормление, деление и бустеры по настоящим WebSocket из отдельных процессов; прежний режим генерирует команды по тикам. Эти сценарии нельзя смешивать в одном A/B. `ROOM_BENCH_SCENARIO=balanced-split` начинает с 35 равных игроков по 16 частей; обычный сценарий использует разные массы и число частей. Оба сохраняют действующую физику, смерти и реальные расходы инвентаря.

Для будущего онлайна 120 000 потребуется распределение примерно 3429 заполненных комнат по нескольким узлам. Количество узлов определяется замерами, а не фиксированной оценкой игроков на VPS. Предполагаемые границы: каталог/резервирование, узлы комнат, владельцы профилей, долговечное хранилище и отдельные проекции рейтингов. Сейчас `/api/arena-reservations` уже выдаёт одноразовый билет и адрес комнаты внутри одного узла.

Хеш профиля определяет логический раздел, но сам по себе не даёт права записи. Передача раздела требует версии маршрутизации и долговечного fencing token; старый владелец теряет право публиковать изменения. Подарки, браки, кланы и общие награды требуют отдельного протокола операций между владельцами. Реестр с TTL пригоден для поиска узлов, но не заменяет долговечное владение экономикой. Настройки Linux, Redis и шардирование MongoDB вводятся по выявленному ограничению и измерениям.

При таймауте бустера исход неизвестен: повторяется исходный идентификатор, а не создаётся новое списание. В прототипе проверены повтор во время fsync, потерянный/задержанный ACK и однократное применение после получения подтверждения. Падение процесса между долговечным списанием и физическим эффектом требует явного протокола восстановления; наличие записи о списании само по себе не доказывает доставку эффекта. Пока этот переход и передача владения не реализованы и не проверены, прототип не заменяет рабочий сервер.
