Правила изменений мира и сохранения прогресса — 25.11.2026

Новые игровые действия должны изменять только свои записи. Одиночные покупки,
инвентарь и личные награды идут через ProfileStore.transactProfile; связанные
действия используют transactWorld с явно вычисленным набором profileIds/clanIds.
Набор вычисляется после refreshCompetition, из актуального опубликованного мира.
Не делать clone/structuredClone/JSON round-trip всего мира в HTTP/WS обработчике
или такте арены. Общие таблицы копируют ссылки; глубокие копии ограничиваются
изменяемыми ветвями. Проверка world-transaction-boundaries не позволяет добавить
штатный вызов transactWorld без набора участников. Она не заменяет проверку
записей через косвенные ссылки и новые обработчики.

Произвольный callback без подтверждённого контракта сохраняет полную изоляцию.
Нельзя просто заменять глубокое копирование на {...world}: callback может изменить
общую вложенную запись до проверки или до отказа сохранения. Режим profileDraft
"clan" разрешён только проверенным командам ClanService. Покупка кланового набора
по-прежнему включает всех получателей, даже отсутствующих в сети. Обновления
профилей остальных участников сохранены; их календарные награды не пропускаются.

Клановый черновик находится в src/server/clans/clan-draft.js. Истории memberHistory
и battleHistory неизменяемы: добавление заменяет массив, прежние записи остаются
общими. Одна реализация используется клановой транзакцией и календарным расчётом.
Все прочие поля, включая неизвестные будущие поля ивентов, копируются приватно.
Общий transactWorld с пользовательским callback не получает этот режим автоматически.
Правки старых записей архива требуют отдельного изолированного пути, как миграции.

Подтверждение успешной операции отправляется после долговечной записи WAL.
Публикация состояния, изменение баланса/инвентаря, квитанция и достижения составляют
один результат. Повтор requestId возвращает прежний результат, другая операция с
тем же ID отвергается. Не переносить подтверждение перед fsync ради измерений.
Не менять правила личного лимита и кланового зачисления ради уменьшения нагрузки:
учитываются реально начисленные XP/киллы; вклад арены попадает в клан после выхода
до закрытия задания/битвы, согласно решению владельца.

Реальное списание обычной валюты в новом ивенте должно использовать общий учёт трат.
Не засчитывать токены как эфир и не считать повтор квитанции второй покупкой.
Проверять бесплатную операцию, недостаток средств, частичный отказ, потерю ответа,
повтор после перезапуска, достижения и выдачу всем получателям кланового набора.
Не исправлять неизвестную историческую недостачу выдуманными компенсациями.

Полные чтения при запуске, восстановлении, миграции, сверке PostgreSQL и резервном
копировании сохраняются. Это не копирование мира на каждый такт. Обмен с PG-worker
использует закреплённое описание снимка/WAL; экспериментальные обработчики комнат
и мира нельзя включать по факту наличия их кода в репозитории. Production использует
журнал и incrementalSettlement; fallback записи целого JSON нужен отдельным offline
инструментам, а не активному серверу.

Проверки соразмерны изменению: CSS — затронутые браузерные сценарии; сохранения —
замороженное предыдущее состояние, отказ записи, повтор и восстановление. Для общего
механизма один полный набор и соответствующая PG-интеграция; повторять весь набор
только при новой общей правке. Локальные изменения после полного прогона проверять
затронутыми файлами, сохранять исходные результаты и точный состав проверенной версии.
Нагрузочные лестницы нужны для ёмкости/такта, не для каждой правки стиля или текста.

Инвентаризация: node games/heroes-of-ether/scripts/testing/audit-world-copies.cjs.
Она разбирает JS в src/public и перечисляет копирование, сериализацию, IPC и границы
транзакций. Растры/данные не изменяет; статический список не доказывает отсутствие
всех косвенных копий. Узкие измерения описывают свой сценарий, не FPS/CCU всей игры.
Полная таблица ссылок профилей, холодное чтение БД и независимое размещение комнат
остаются отдельными архитектурными задачами; готовность к 300000 CCU не доказана.
